🏛️ ملخّص تنفيذي

النظام منصّة تعليمية متعددة المدارس (Multi-Tenant) مبنية على ثلاث طبقات مترابطة بذكاء، تحوّل تطبيقات Google Apps Script من واجهة google.script.run إلى واجهة fetch ثابتة تعمل دون VPN ودون اتصال.

الخلاصة بثلاث جُمل

١. المعمارية ذكية واقتصادية: لا خادم مدفوع — Google Sheets كقاعدة بيانات، GAS كـ API، GitHub Pages للواجهة، وCloudflare Worker لتجاوز حجب اليمن، مع طبقة PWA للعمل دون اتصال.

٢. أبرز خطر: طبقة الحماية الفعلية في ApiEndpoint.js تعتمد قائمة منع (blocklist) لا قائمة سماح (whitelist) كما يوحي التوثيق — ما يسمح باستدعاء دوال إدارية حسّاسة من أي زائر مجهول.

٣. النسخة المحلية C:\SchoolApp غير متزامنة مع GitHub (تنقصها frontend/ وworker/ وملفات ApiEndpoint.js والملفات الرئيسية لعدة مشاريع) — يجب توحيد المصدر قبل أي عمل.

قاعدة الالتزام: هذا التقرير تدقيق وفهم فقط — لم يُعدَّل أي سطر، ولم تُلمَس معرّفات النشر (Deployment IDs). كل توصية أدناه قابلة للتنفيذ لاحقاً وبشكل آمن وتدريجي.

🧭 خارطة طريق التحسين (متدرّجة وآمنة)

المرحلة 0 — التوحيد (الآن · بلا تغيير كود)
إزالة الغموض وتأمين نقطة انطلاق موثوقة.
  • مزامنة C:\SchoolApp مع GitHub واعتماد المستودع مصدراً وحيداً للحقيقة.
  • أخذ نسخة احتياطية كاملة للأوراق ومعرّفات النشر قبل أي خطوة لاحقة.
  • اعتماد هذا التقرير كخط أساس (baseline) موثّق.
المرحلة 1 — الأمان (الأعلى أولوية)
سدّ ثغرة استدعاء الدوال الإدارية.
  • تحويل ApiEndpoint.js لاستخدام قائمة السماح whitelist.json فعلياً بدل قائمة المنع.
  • إزالة eval() واستبداله بخريطة دوال صريحة (function map).
  • اشتراط التوكن على كل دالة كتابة/إدارة (لا الاكتفاء بلاحقة Protected).
  • نقل المعرّفات الحسّاسة خارج المستودع العام أو إقرار نموذج "عام بحماية دوال".
المرحلة 2 — الصحّة الوظيفية
إغلاق التبعيات المكسورة.
  • تنفيذ checkSession وgetStudentsForView أو إزالة استدعائهما من الواجهة.
  • إضافة Terms.html أو حماية مسار ?page=terms.
  • تعبئة قائمة دوال API لمنصّة schedule.
المرحلة 3 — قابلية الصيانة
القضاء على التكرار.
  • توحيد DriveUrlUtils وDeploymentRegistry في مصدر واحد يُولَّد عبر _build/.
  • إصلاح ترويسة cms/_Tenant.js وحذف ملفات «بلا عنوان» وفصل ملفات الاختبار.
المرحلة 4 — المتانة
تقوية الاتساق دون اتصال.
  • إضافة منع تكرار خادمي عبر opId في CacheService (24 ساعة).
  • إبطال كاش تلقائي عند الكتابة بدل المسح اليدوي.
  • تضييق نطاق تجريد CSP في الـWorker على الضروري فقط.

🛡️ استراتيجية إعادة الهيكلة الآمنة

مبادئ تضمن عدم كسر التوافق إطلاقاً أثناء أي تطوير لاحق.
  • فرع لكل تغيير: لا تعديل مباشر على main؛ مراجعة عبر Pull Request.
  • ثبات معرّفات النشر: أبقِ على نفس Deployment ID دائماً (Manage deployments → Edit → New version) لتبقى روابط /exec والـWorker صالحة.
  • مشروع واحد في كل مرّة: عدّل مشروع GAS واحداً واختبره عبر ?action=health قبل الانتقال للتالي.
  • المصدر الواحد: استخدم سكربتات _build/ لتوليد ApiEndpoint.js والواجهة بدل التحرير اليدوي المتكرر.
  • مدرسة تجريبية: أضف صفّ مدرسة اختبار في سجل Master للتحقق قبل لمس مدارس الإنتاج.
  • تحقق آلي: سكربت يقارن قائمة الدوال العامة فعلياً مقابل whitelist.json ويُنبّه على أي انكشاف جديد.
  • تراجع فوري: بما أن النشر بالإصدارات، يمكن الرجوع لإصدار سابق من نفس الـDeployment خلال ثوانٍ.
التوافق مع ES5: الخلفية ملتزمة بالقواعد الصارمة (var، بلا دوال سهمية، بلا قوالب نصية). لكن gas-bridge.js يستخدم Proxy (ES6) — مقبول في المتصفّحات الحديثة، لكن تحقّق من حدّ WebView الأدنى في تطبيق أندرويد لتفادي كسره على الأجهزة القديمة.
